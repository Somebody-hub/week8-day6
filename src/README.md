# Практический проект: Трекер задач с базой данных (День 6)
## Что было сделано и ключевые решения

---

### 1. База данных и схема (Flyway)
* Отказался от автогенерации схемы Hibernate (`ddl-auto: validate`).
* Вся схема описана вручную в двух миграциях:
    * `V1__init.sql` — таблица `tasks` с индексами по статусу и приоритету.
    * `V2__task_tags.sql` — таблица связей `task_tags` с внешним ключом `ON DELETE CASCADE` и ограничением уникальности `uq_task_tags (task_id, tag)`.
* Идентификаторы генерируются базой (`BIGSERIAL` / `IDENTITY`), время создания фиксируется сервером БД.

### 2. Производительность и решение проблемы N+1
* Намеренно отключил Open-in-View (`spring.jpa.open-in-view=false`), чтобы исключить неконтролируемые запросы при сериализации в JSON.
* Сущность `Task` инкапсулирует коллекцию тегов как `@ElementCollection`. Чтобы при пагинации не возникало проблемы N+1, добавил аннотацию `@BatchSize(size = 50)`.
* В результате при запросе страницы задач (`page=0&size=2`) приложение выполняет **ровно 3 SQL-запроса**:
    1. Выборка страницы задач (`LIMIT` / `OFFSET`).
    2. Подсчет общего количества (`COUNT`) для метаданных пагинации.
    3. Пакетная загрузка всех тегов для полученных задач через `task_id = ANY(?)`.
* Для точечного чтения (`findById`) используется `@EntityGraph(attributePaths = "tags")`, вытягивающий задачу с тегами за 1 запрос через `LEFT JOIN`.

### 3. Бизнес-правила и транзакции
* Сервисный слой полностью закрыт `@Transactional(readOnly = true)`. Модифицирующие методы помечены `@Transactional`.
* Статусы и приоритеты хранятся строками (`EnumType.STRING`).
* Реализовал матрицу допустимых переходов статусов: задача создается в статусе `NEW`, может переходить в `IN_PROGRESS` или `CANCELLED`. Финальные статусы менять нельзя — при попытке выбрасывается `StatusTransitionException` (400 Bad Request).
* Статистика считается на уровне базы данных через агрегирующие JPQL-запросы с `GROUP BY` и проекции (`StatusCount`, `PriorityCount`). В память приложения лишние данные не выгружаются.

## Проведенные проверки

Все сценарии оформлены в файле `requests.http` в корне проекта. В ходе ручного тестирования и профилирования я проверил:

1. **Персистентность данных:**
    * Создал 3 задачи, полностью остановил приложение, запустил заново — все задачи и связанные с ними теги сохранились в PostgreSQL.
2. **Откат транзакций:**
    * Проверил атомарность: при возникновении исключения в середине транзакции изменения откатываются (`rollback`), частичных данных в базе не остается.
3. **Контроль дубликатов тегов:**
    * Повторный запрос на добавление уже существующего тега возвращает `409 Conflict`, а в таблице `task_tags` дублирующая строка не появляется.
4. **Каскадное удаление:**
    * При удалении задачи через `DELETE /api/tasks/{id}` теги удаляются каскадно на уровне СУБД. Проверил это прямым запросом в базу:  
      `SELECT * FROM task_tags WHERE task_id = ?;` — возвращает ровно `0 rows`.
5. **Фильтрация, поиск и пагинация:**
    * Поиск по части названия `q` работает без учета регистра (`LOWER(...) LIKE %...%`).
    * Запрос с фильтром, под который ничего не подходит, возвращает статус `200 OK` и пустой массив `[]` в поле `content` (а не `404`).
    * Запрос с параметрами `page=0&size=2` отдает ровно 2 элемента в выборке и корректное общее количество задач в `totalElements`.
    * Сортировка `sort=priority,desc` корректно меняет порядок сущностей в ответе.
6. **Анализ SQL-логов и N+1:**
    * В логах Hibernate проверил число запросов на одну страницу списка (`page=0&size=2`). Выполняется **ровно 3 запроса** (выборка сущностей, `count` для пагинации и пакетный запрос тегов через `ANY(?)` благодаря `@BatchSize`).
